Static analysis tells you what a binary could do; dynamic analysis proves what it actually does. When malware unpacks itself in memory, decrypts strings at runtime, or runs through complex anti-reversing checks, a debugger is your most potent instrument.

To master dynamic analysis, you must understand how debuggers (like GDB, x64dbg, and WinDbg) manipulate the CPU at the hardware and kernel levels.

The Secret Mechanics of Software Breakpoints (INT 3)

When you type break *0x401120 in GDB or press F2 in x64dbg, the debugger does something counter-intuitive: it alters the target program’s memory!

  1. Byte Substitution: The debugger saves the original byte at address 0x401120 (say, 0x55 for push rbp) and replaces it with byte 0xCC (the opcode for INT 3).
  2. The Trap: The CPU executes forward. When RIP hits 0xCC, the CPU triggers hardware interrupt vector 3 (Breakpoint Exception).
  3. Process Halting: The kernel halts the target process and delivers a SIGTRAP signal to the debugger.
  4. State Restoration: The debugger replaces 0xCC with the original 0x55, rolls RIP back by 1 byte, and waits for your commands!

Hardware Breakpoints (Debug Registers DR0–DR7): Software breakpoints fail if code is placed in read-only memory or if malware performs memory integrity checksums (scanning for 0xCC bytes). To bypass this, processors include dedicated hardware debug registers: DR0, DR1, DR2, DR3 hold memory addresses, while DR7 defines whether to trigger on Execution, Data Write, or Data Read/Write (Watchpoints). Hardware breakpoints never modify memory bytes!

Single-Stepping & The Trap Flag

How does a debugger let you step instruction-by-instruction (Step Into / F7)?

Inside the 64-bit RFLAGS register sits bit 8: the Trap Flag (TF).

speedTF = 0Normal continuous CPU execution
pest_controlTF = 1Single-step mode enabled

When TF is set to 1, the processor executes exactly one instruction and immediately raises a single-step exception (Interrupt 1), returning control to the debugger after every single opcode!
