Raw machine code cannot simply be dumped onto a disk and executed. The operating system loader needs a structured container specifying memory layouts, permissions, imported dynamic libraries, symbol tables, and the initial execution entry point.

In cybersecurity and malware analysis, you will encounter two primary binary formats:

terminalELFLinux / Unix / Android
desktop_windowsPE / PE32+Windows Executables & DLLs

Segments vs Sections: In an ELF binary, Sections (like .text, .data, .rodata) exist for the compiler, linker, and reverse engineer. Segments (defined in Program Headers, like PT_LOAD) exist for the OS kernel loader, defining whether memory is mapped Read (R), Write (W), or Execute (X). Striping section headers does not prevent execution, but it strips disassembler clues!

The Dynamic Resolution Engine: PLT and GOT

Binaries rarely bundle all library code inside themselves. They dynamically link against shared libraries (like libc.so.6 or kernel32.dll):

  1. PLT (Procedure Linkage Table): A jump table located in .plt. Each entry consists of small stub instructions that jump to an address read from the GOT.
  2. GOT (Global Offset Table): An array of absolute pointers stored in writable memory (.got.plt).
  3. Lazy Binding: The first time printf() is called, the GOT entry points back to the dynamic linker (`_dl_runtime_resolve`). The linker looks up the real libc address in memory, writes it into the GOT, and executes it. Subsequent calls jump straight through the GOT with zero overhead!
